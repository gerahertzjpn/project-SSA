# ADR-0001: Population-18 free-agent draft pool через frozen-snapshot self-play

Дата: 2026-06-09
Статус: принято (подготовлено к запуску; обучение ещё не проводилось)

Контекст: нужно подготовить тренировку 18 уникальных нейросетей — «1 сид = 1
игрок», по 6 на каждую из 3 фракций. Каждая сеть должна играть на любой позиции
с любым союзником, быть максимально уникальной; ключевая механика — self-play;
отбор/culling сейчас запрещён. Существующий командный тренер обучал фиксированное
трио {A1,A2,A3} только за фракцию humans.

Пользовательские развилки (зафиксированы вопросом):
- состав команд: **только микс-фракции** (любые 3 сети из 18);
- self-play: **frozen-snapshot ротация** (переиспользуем протестированный путь);
- уникальность: **seed + разный рецепт** (без вариаций архитектуры).

Решение:
- 18 faction-locked сетей `MaskedActorCritic` (hidden 128, единый интерфейс
  `train_obs_v3.1`), 6 рецептов (lr/entropy/clip) × 3 фракции, уникальные сиды →
  18 различных genotype_hash. Спецификация — `build_default_population()`.
- Аддитивно расширил `TeamTrainingEnv`: `player_factions` (фракция per-slot,
  следует за сетью при рандомизации позиции) и `opponent_policy_state_ids` (per-
  slot frozen-оппонент из общего pool-чекпоинта). Обратносовместимо (default =
  humans, без state_ids = legacy).
- Новый изолированный нативный тренер `src/training/population.py` +
  `scripts/train_population.py`: per-episode сэмплит микс-фракционную тройку
  обучаемых (team A, рандом позиции) против 3 frozen-снапшотов (team B);
  переиспользует `update_policy`/GAE/`PolicyBot`. Frozen pool обновляется каждые
  N апдейтов. Без отбора: все 18 чекпоинтятся каждый раунд.

Последствия:
- Плюсы: не тронут общий командный тренер (нет регрессий); полное переиспользование
  протестированного RL-ядра; чистая модель «1 сеть = 1 драфт-кандидат» (каждый
  `nets/<id>/latest.pt` грузится `PolicyBot`-ом). 
- Минусы/долги: тренер контролирует только team A (B-side через зеркалирование
  observation), live-both-sides self-play не реализован; throughput-долг
  (~1.9M шагов/час) остаётся; milestone-чекпоинты занимают место.

Проверка: 9 новых тестов (`tests/test_population.py`: uniqueness, faction env,
frozen pool round-trip, scheduling coverage, 1-update smoke) + 49 существующих
зелёные; smoke (1 и multi-worker), resume и full-length sanity (реальные
win/loss) прошли.

## 2026-06-10 — Regionals: ключевые решения

1. **Всё симулируется при создании, включая плей-офф.** Лига и так считается
   заранее; посев плей-офф известен сразу после симуляции лиги, поэтому SF и
   финал играются в том же job. День-гейтинг — чисто презентационный. Следствие:
   персистентные эффекты (Elo, деньги, титулы, h2h) применяются к реестрам в
   момент создания; глобальная страница «Игроки» может «спойлерить» итоги
   текущего турнира — осознанная упрощёнка v1.
2. **Ничья в Bo5-серии плей-офф → проходит команда с более высоким посевом**
   (движок умеет ничьи в играх). Зафиксировано в тестах.
3. **Импакт в Elo ограничен ±20% от базовой дельты** — основа рейтинга всё ещё
   победа/поражение (требование ТЗ); прокси импакта: выживание + core_hp +
   ресурсы относительно своей тройки (per-player урона по ядру в статах нет).
4. **Драфт-порядок: случайный пер-раунд с запретом повторной позиции** — и
   случайно, и сбалансированно, без снейка.
5. **Атрибуты карточек выводятся из реальных eval-данных** (population_balance
   per-net winrate/механики) и снапшотятся в реестр: карточки стабильны даже
   если analysis/ пересоберут; fallback — профиль по рецепту обучения.
6. **LLM опциональна по построению**: инжектируемый клиент (тесты — fake),
   авто-пик при сбое, комментарии только по кнопке и кэшируются. Модель —
   `claude-opus-4-8`, промпты компактные (карточка = 1 строка), structured
   output с enum id для драфта.

# ADR-0002: Защита ядра — авто-подкрепление + overflow по слоям

Дата: 2026-06-14
Статус: принято

Контекст: при бое за ядро резерв (особенно юниты, произведённые во время осады)
простаивал в node.units рядом с боем — движок забирал стационарные юниты узла в
бой только один раз, при его создании (KI-001, подтверждено на league-реплеях:
idle-армия у осаждённого ядра на 81% тиков боёв за ядро). Просто начать
докидывать произведённые юниты в бой нельзя — это даёт бесконечную осаду: один
юнит в тик «держит» всю армию, потому что излишек урона по фронтовому юниту
пропадал (overflow не было).

Решение:
- **Авто-подкрепление (вариант пользователя №1):** `_absorb_stationed_units_into_battle`
  в каждом тике `_tick_active_battles` забирает в активный бой узла новые
  node.units/visiting_units владельца (если в бою есть враг), тем же путём, что и
  приходящие группы.
- **Overflow при защите ядра:** `combat2d._apply_core_defense_overflow`. Суммарный
  урон, нанесённый за тик стороне владельца ядра, переливается по приоритету
  **войска → здания → ядро**:
  - войска переполняются свободно (токен-юнит больше не держит армию);
  - здания — «пластины»: за тик гибнет только внешнее здание, излишек сверх его HP
    НЕ проливается на следующее здание/ядро (ядро не падает за один тик; ядро за N
    зданиями держит ≥ N тиков штурма);
  - ядро уязвимо только когда зданий не осталось.
  Чтобы фронтовой слой собирал весь урон армии (а не «пропускал» атакующих после
  лет­ального пинга), войска защитника в бою за ядро помечаются ролью
  `active_layer` (sticky) в `_core_structure_target_role`.

Последствия:
- Дрип 1 юнит/тик держит малую армию (≈20), но крупная (≥~50) пробивает через
  пластины за несколько тиков. Точный порог — баланс-ручка (HP зданий), подгонится
  тренировкой. Изменение строго ограничено боями `objective=="core"` — PvP/edge/
  neutral не затронуты.
- Интерфейс obs/action не менялся (`train_obs_v3.1`) → существующие чекпойнты
  совместимы, возможна **дотренировка** (`train_team_policy.py --resume <ckpt>`),
  не обязательно обучение с нуля.
- В `rules_meta()` добавлены флаги `stationed_reserves_join_active_battle` и
  `core_defense_damage_overflow` — реплеи/раны самодокументируются.

Проверка: 2 новых интеграционных теста (absorb + «дрип не держит крупную армию,
но держит малую»); существующий `test_core_assault_can_destroy_only_one_building_layer_per_tick`
сохранён зелёным (пластины не сломаны); полный прогон 330 passed (1 фейл —
start_viewer.ps1, чужой WIP); training smoke и `--resume` дотренировка (1 апдейт,
GPU, без NaN) прошли.

# ADR-0003: Dense reward за добивание ядра (core_progress shaping)

Дата: 2026-06-16
Статус: принято

Контекст: анализ регионалс показал массовую пассивность — в 39% игр сеть держит
крупную армию рядом со слабо защищённым вражеским ядром и НЕ добивает (худший —
infected_6: 93 юнита у голого ядра 88 тиков, проигрыш). Причина в награде: ядро
влияло на shaping только через бинарный терм `alive` (скачок в момент смерти
ядра); за «продавливание» 80→1 сигнала почти не было → finish — разреженный
джекпот, который RL плохо учит. Требование: добавить бонус ОЧЕНЬ аккуратно —
чтобы не все стали пушерами и длинные тактики оставались жизнеспособными.

Решение: `core_progress_weight` (default 0.5) в TeamTrainingEnvConfig /
TeamPPOConfig / PopulationConfig + CLI `--core-progress-weight`. В `_team_score`
— симметричный терм: доля снесённого HP каждого ядра (вражеские +, свои −),
нормировка на размер команды, складывается в уже существующий телескопирующий
shaping.

Почему не превратит всех в пушеров:
- Потенциальная награда: shaping = разница score между тиками, core-терм
  телескопируется к финалу → не меняет оптимальную политику, лишь уплотняет
  сигнал (фикс разреженности, не новая цель).
- Симметрия: продавил чужое = +, подставил своё = − на ту же величину → голый
  пуш штрафуется так же; защита/макро остаются выгодными, награждается победа в
  «гонке ядер» (= условие победы).
- Масштаб: полный килл = +0.01 reward/тик (vs терминал ±1), суммарный shaping за
  игру ~5% терминала → гайд, а не джекпот; «выиграй игру» остаётся главной целью.
- Тюнится: 0.25 мягче, 0 выкл.

Проверка: test_core_progress_shaping_is_dense_symmetric_and_disableable
(плотность/симметрия/масштаб/выключаемость) + 80 train/combat тестов зелёные.
Интерфейс obs/action не тронут → совместимо с дотренировкой.

Открытый вопрос (Лорд): по регионалс Baron не трогают в 59% игр, Лорд
появляется в 12%, доходит до ядра в 5%, но когда срабатывает — выигрывает
(d05_g0: соло снёс 2 ядра). Похоже на недотренированность пайплайна
Baron→escort→core, а не на сломанную механику. Reward-shaping за Baron/Лорда
и/или тюнинг Baron — отложено до решения пользователя.

# ADR-0004: Очень лёгкий ребаланс фракций (robots up, humans чуть down)

Дата: 2026-06-16
Статус: принято (применено; требует перетренировки + повтор аудита для оценки)

Контекст: аудит population-18 (analysis/POPULATION_18_BALANCE_FINDINGS.md,
1340 матчей) — pure H2H winrate humans 0.833 / infected 0.542 / robots 0.125.
Корень: «равное золото даёт роботам вдвое меньше армии» (cheapest body: infected
SWARMLING=1, humans SKIRMISHER=2, robots DRONE=6) + слабый старт роботов
(1 медленный WALKER vs 6 SWARMLING / 2 VANGUARD). Бои решает число тел.
Пользователь выбрал вариант «robots fix + лёгкий нерф humans».

Решение (3 числа, всё в константах, обратимо):
- robots DRONE cost 6 -> 4 (constants.py): HP/gold и DPS/gold 1.0 -> 1.5
  (infected SWARMLING 2.0, humans SKIRMISHER 1.5/2.0) — закрывает большую часть
  разрыва по телам, не доводя до паритета.
- robots старт 1 -> 2 WALKER (state.py _starting_units_for_faction) — лечит
  слабый медленный опенинг.
- humans RANGER atk 10 -> 9 (units.py) — намеренно САМЫЙ мягкий нерф (−10% на
  одном юните). Escalation, если humans останутся сверху после аудита:
  SKIRMISHER cost 2 -> 3 (нерф по числу тел, тяжелее).

Почему так: целимся ровно в задокументированный корень (число тел), минимальная
поверхность, R-P-S не ломается (тест на side-симметрию зелёный). Точные числа —
догадка, валидируются повтором scripts/population_balance_test.py.

Последствия / процесс:
- Сети учились на старой экономике → нужна перетренировка/дотренировка ПЕРЕД
  оценкой. Workflow: rebalance -> retrain -> re-audit (population_balance_test.py).
- Интерфейс obs/action не тронут; rules_meta уже пишет unit_cost/unit_stats →
  реплеи/раны самодокументируют экономику.

Проверка: 333 passed (1 фейл — start_viewer.ps1, чужой WIP); pinned-тест старта
роботов обновлён (1->2 WALKER); headless-матч на новой экономике без падений.
